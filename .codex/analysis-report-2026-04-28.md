# SublinkPro 架构与任务系统分析报告

生成时间：2026-04-28

## 结论先看

这套项目是一个单仓库全栈应用。后端用 Go + Gin + GORM，前端用 React 19 + Vite + Material UI。核心业务是围绕订阅源、节点、测速、标签规则、分享订阅、链式代理和通知系统展开。项目整体分层还算清楚，缓存层和任务层也都做了拆分，但任务系统，尤其是自动更新订阅这条链路，存在几个比较实在的问题。

这次重点排查后，和你提到的现象最贴近的不是单一小毛病，而是一组连锁问题。前端根本不给订阅更新任务显示停止按钮。后端虽然有通用停止接口，但订阅更新任务实际没有接入取消语义。更麻烦的是，任务最终状态写库失败时，内存任务会被清掉，数据库里却可能永久停留在 running。任务页历史列表主要看数据库，所以会出现任务已经不跑了，但页面还能一直显示运行中的状态。这个现象和用户反馈高度吻合。

## 一、项目整体架构

后端入口在 `main.go`。启动顺序大致是加载配置、初始化数据库、跑迁移、初始化各种缓存、初始化任务管理器和 scheduler 依赖、启动 SSE、再注册 API 路由和前端静态资源服务。前端 build 产物最终会被复制到 `static/`，生产构建再由 Go 二进制嵌入并对外提供。

后端结构按职责拆得比较明确。`api/` 负责 HTTP 入口。`models/` 负责数据库模型、缓存同步和部分聚合查询。`services/` 负责任务管理、通知、mihomo 集成、调度、数据库迁移等后台逻辑。`node/` 负责协议解析、订阅拉取和节点转换。`routers/` 负责 API 注册。

前端结构也比较标准。`webs/src/views` 是页面级功能，`webs/src/api` 是请求边界，`webs/src/components` 承载大量共享 UI。任务中心在 `webs/src/views/tasks/index.jsx`，悬浮任务进度面板在 `webs/src/components/TaskProgressPanel.jsx`，实时任务状态来自 SSE 和 `TaskProgressContext`。

从运行时设计看，这个项目明显偏重缓存驱动。节点、订阅、机场、标签、任务、模板、分享链接等都在启动时进入内存缓存，后续读请求大量走缓存，写操作走 Write-Through。这个思路对读性能有帮助，但也放大了任务并发、状态一致性和缓存快照构建的成本。

## 二、自动更新订阅任务的实际执行链路

自动订阅更新由 `services/scheduler/manager.go` 里的 cron 回调触发。调度器从数据库加载所有启用的机场订阅，然后给每个机场注册一个 cron 任务。每次触发时直接调用 `ExecuteSubscriptionTask`。

`ExecuteSubscriptionTaskWithTrigger` 位于 `services/scheduler/subscription_task.go`。这里会读取机场配置，创建一个 `TaskManager` 任务记录，然后把 reporter 传给 `node.LoadClashConfigFromURLWithReporter`。

真正的大活在 `node/sub.go`。它先下载订阅内容，整包读入内存，再尝试按 YAML、Base64 或逐行链接解析出代理节点。解析完后调用 `scheduleClashToNodeLinks`。这一步会做过滤、去重、重命名、唯一化、批量新增、批量更新、批量删除、回写机场统计，最后通过 reporter 上报完成状态。

前端任务页一共看两类数据。顶部实时进度区看的是 SSE 内存态。历史列表看的是数据库任务表，再把当前仍存在于内存中的 running 任务覆盖到列表结果上。这个设计本身没错，但它对终态落库的可靠性要求很高。一旦终态没写进去，页面就会出现假运行中。

## 三、和用户反馈直接相关的 bug

### 1. 订阅更新任务没有停止按钮，前端把它硬编码排除了

这个问题是确定存在的，不是猜测。

在 `webs/src/components/TaskProgressPanel.jsx` 里，任务是否可停止被写死成 `task.taskType === 'speed_test'`。在 `webs/src/views/tasks/index.jsx` 的表格区，停止按钮也只对 `speed_test` 且 `running` 的任务显示。也就是说，`sub_update`、`tag_rule`、`db_migration` 虽然共享同一套后端停止接口，UI 却根本不给入口。

后端其实已经提供了通用接口 `POST /api/v1/tasks/:id/stop`，定义在 `api/task.go`。所以当前状态不是后端没有能力，而是前端直接没放出来。用户说看着难受，这个反馈完全成立。

### 2. 就算手动调停止接口，订阅更新任务也不是真的可取消

这也是确定存在的。

`TaskManager.CreateTask` 会给任务创建 `context.Context`。测速任务 `speedtest_task.go` 在执行过程中会反复检查 `ctx.Done()`，所以能比较像样地停下来。但订阅更新任务在 `services/scheduler/subscription_task.go` 里创建任务后，把返回的 `ctx` 直接丢了，后续链路没有任何地方检查取消信号。

`node/sub.go` 里的下载、解析、批量处理、节点写入、去重、删除，都没有取消检查。结果就是接口层把任务状态改成了 cancelled，真实工作线程却还会继续跑完。这个会造成两层错位。界面状态和实际执行不一致。后续资源占用也不会立刻降下来。

### 3. 任务最终状态写库失败时，会留下长期 running 的脏记录

这是我认为最可能导致“好几天也不结束”的根因。

`services/task_manager.go` 里的 `CompleteTask`、`FailTask`、`CancelTask` 都会调用 `running.Task.SyncFinalStatus()` 把最终状态写回数据库。但如果这一步失败，代码只是打一条日志，然后继续广播 SSE，继续 cancel context，继续在 500ms 后把内存里的 running task 删除掉。

也就是说，任务已经从内存运行列表里消失了，但数据库里的 `status` 还可能停留在 `running`。任务列表页的历史表格是以数据库记录为主，所以这个任务会长期显示成运行中。只有服务重启时，`InitTaskManager` 里的 `MarkRunningTasksAsError()` 才会把数据库里残留的 running 改成 error。

这个缺口之所以危险，是因为订阅更新本身就是重写压力比较大的任务。它在一次执行里会做批量新增、批量更新、批量删除、机场统计更新、缓存同步。默认数据库又是 SQLite。SQLite 已经设置了 `_busy_timeout=5000` 和 WAL，但 `SyncFinalStatus` 本身没有重试包装，也没有事务级兜底，只要撞上锁冲突或瞬时 DB 异常，就可能把任务永远留在 running。

这和用户看到的现象非常贴。

### 4. 调度器没有同机场任务重入保护，任务能重叠执行

这个问题会放大上面那个脏状态 bug，也会放大资源消耗。

`services/scheduler/manager.go` 的 cron 回调是直接调用 `ExecuteSubscriptionTask`。这里没有任何“同一个机场已有订阅更新任务正在运行就跳过”的检查。也没有全局并发阈值。只要 cron 到点，新的任务就会起。

如果某个机场订阅本身很大，或者上一次任务因为锁等待、远程链接慢、批量更新慢而拖长，下一个周期又会继续进来。多次重叠后，SQLite 锁冲突概率会更高，最终状态写库失败概率也会更高，running 脏状态就更容易留下来。

### 5. 当前仓库自动化测试本身已经暴露了并发回归

我用你本机的 Go 版本跑了 `go test ./...`。大部分包能过，但 `api` 包失败了，失败用例是：

`TestGetClientConcurrentClashRequestsKeepSubscriptionScoped`

`TestGetClientConcurrentSurgeRequestsKeepSubscriptionScoped`

报错都是 `unexpected ... response body: "配置读取错误"`。

这说明 `/c` 订阅导出链路在并发场景下现在就有回归，没有稳住。它和自动更新订阅不是同一条链路，但都属于订阅域，说明这一块的并发隔离和状态边界需要认真看。

## 四、资源占用分析

### 单次订阅更新的资源模型

单次更新本身不是“离谱级”消耗，但绝对不是轻量任务。

下载阶段会把整个响应 `io.ReadAll` 一次性读进内存。随后会再构建一份 `config.Proxies` 切片。进入 `scheduleClashToNodeLinks` 后，还会再建多组 map，包括现有节点表、按 hash 的索引、按名称的索引、本次 hash 集合、当前名称集合、历史名称集合、全库 hash 集合、待新增列表、待更新列表、待删除列表。整体空间复杂度接近 `O(当前订阅节点数 + 当前机场已有节点数 + 全库节点数)`。

如果机场订阅规模在几百到一两千节点，这种开销通常还算可接受。真正常态压力源不是单次解析，而是“每次都扫全库哈希”和“任务重叠”。

### 最重的几个点

最重的点在 `models.GetAllNodeContentHashes()`。当跨机场去重开启时，每次订阅更新都会遍历整个节点缓存，重新构造一份全库 hash 集合。这一步和当前机场规模无关，而是和全站总节点数正相关。节点量越大，这一步越贵。

第二个点是 `BatchUpdateNodeInfo` 名字叫 batch，实际上内部是一条条 `UPDATE`。如果某次同步里有很多节点只是改名、改链接或改排序，这里会产生较多数据库往返。

第三个点是同步完成后还会异步触发一次 `applyAutoTagRules`。它会再次读取该机场节点，并执行规则扫描。也就是说，订阅更新刚结束，CPU 和数据库压力并没有真的归零。

### 综合判断

如果只看单次执行，资源占用属于中等偏上，不算爆炸。真正会把机器拖难受的，是这几个条件一起出现时：

订阅节点很多。

全库节点很多。

跨机场去重开启。

cron 周期比较短。

任务允许重叠。

终态写库偶发失败，数据库里留下一堆 running 记录。

在这种组合下，用户看到的就不只是“UI难受”，而是任务和资源都会逐步发散。

## 六、优先级判断

如果按修复优先级排，第一优先级不是美化任务页，而是先堵状态一致性缺口。也就是任务终态落库失败后不能直接把内存任务删掉，至少要有重试、兜底或补偿机制。否则 running 脏状态会一直污染任务中心。

第二优先级是给订阅更新任务加真正的取消语义，不只是展示一个按钮。只有按钮没有取消检查，只会让状态更乱。

第三优先级是给 scheduler 增加同机场任务互斥或跳过策略。否则自动更新订阅在高频 cron 下会自己打自己。

第四优先级才是前端交互，把订阅更新任务的停止按钮和停止中状态补齐。

## 七、最终判断

这个项目主架构没散，业务边界也清楚，属于能继续维护和扩展的底子。问题集中在任务系统的最后一公里。订阅更新任务这条链路现在更像“能跑”，但还没做到“稳”。用户反馈的现象基本不是误报，代码里确实能找到对应原因，而且还是好几个点一起叠出来的。

这份报告对应的最高置信结论有三个。

订阅更新任务现在没有前端终止按钮。

订阅更新任务即使走停止接口，也没有真正接入取消执行。

任务最终状态落库失败时，数据库会留下长期 running 的脏记录，这就是任务页长期显示运行中的核心嫌疑点。
